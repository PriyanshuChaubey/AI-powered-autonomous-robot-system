# Firmware Pipeline — Agents 1 to 3

Three of the five agents, built around a real robotics target: an ESP32
obstacle-avoiding robot whose firmware is generated by the pipeline.

```
mission.txt
    |
    v
[Agent 1  Requirements]  ->  1_requirements.json
    |
    v
[Agent 2  Architecture]  ->  2_architecture.json  + pin_map_report.txt
    |                          (validated, or the build stops)
    v
[Agent 3  Firmware]      ->  robot_controller.ino + firmware_lint_report.txt
    |
    v
  (phase two)  Agent 4 Testing  ->  Agent 5 Review & Repair
```

The two remaining agents slot onto the end with no redesign: Agent 4 takes the
JSON telemetry line the sketch already prints and runs the acceptance tests on
the hardware (or against a simulated serial feed), and Agent 5 reads those
results and feeds them back into Agent 3.

---

## Quick start

```bash
cd firmware_agents
python3 pipeline.py            # mock mode: no API key, no network, ~0.3 s
```

Outputs:

```
artifacts/
  1_requirements.json
  2_architecture.json
  pin_map_report.txt
  firmware_lint_report.txt
  robot_controller/robot_controller.ino
  run_log.json
```

Run the failing cases (this is the demo for the review):

```bash
python3 demo_validator_fail.py
```

Switch to a real model:

```bash
export FIRM_LLM_MODE=openai
export FIRM_LLM_API_KEY=sk-...
export FIRM_LLM_MODEL=gpt-4o-mini
python3 pipeline.py
```

Works unchanged against any OpenAI-compatible endpoint (Groq, Together, or a
local vLLM server — point `FIRM_LLM_BASE_URL` at it). For Ollama, use
`FIRM_LLM_MODE=ollama` and `FIRM_LLM_BASE_URL=http://localhost:11434/v1`.

## What each file does

| File | Role |
|---|---|
| `pipeline.py` | Runs the three stages in order, times them, writes `run_log.json` |
| `agent1_requirements.py` | Free text → testable FR/NFR/HR + Given-When-Then acceptance tests |
| `agent2_architecture.py` | Requirements → components, pin map, power, state machine, timing |
| `agent3_firmware.py` | Architecture → Arduino sketch, then lints it |
| `validators.py` | The ESP32 rules and the firmware lint. **This is the core.** |
| `prompts.py` | Every prompt, in one place, versionable |
| `llm.py` | One client, three modes: mock, OpenAI-compatible, Ollama |
| `mock_data.py` | Golden outputs — lets the demo run offline and pins the JSON contract |
| `hardware_catalog.json` | Board limits and BOM as data, so rules are editable without code |
| `demo_validator_fail.py` | Four injected mistakes, each caught |

## The design decision worth defending

A language model will produce a plausible-looking pin map that is electrically
wrong: GPIO 6 for a motor, two sensors on one pin, a 5 V echo line straight
into a 3.3 V part. Nothing in the prompt reliably prevents that.

So Agent 2 is not trusted to judge its own wiring. The pin map is checked
against `hardware_catalog.json` before it is written:

- GPIO 6–11 → error (internal SPI flash)
- GPIO 34/35/36/39 used as outputs → error (input-only)
- one GPIO used by two signals → error
- GPIO 0/2/5/12/15 as outputs → warning (boot strapping)
- GPIO 1/3 → warning (USB serial)
- servo with no separate supply → warning

Then Agent 3's code is checked against the approved map: every `#define`
constant must map to an approved GPIO, and `delay()` or `pulseIn()` in the
sketch is an error because both stall the loop.

If a stage fails, the error list goes back to the model for one repair round.
If it fails twice, the pipeline exits non-zero and writes nothing further.
That is the difference between "the AI wrote some code" and "the AI wrote code
that passed a gate."

from the battery rail, never from a GPIO.

## Honest limits (say these before the panel asks)

1. **The three agents are code-complete; agents 4 and 5 are not built yet.**
   The testing agent will consume the JSON telemetry line the sketch already
   emits. That is why the telemetry format is in the requirements.
2. **Mock mode returns fixed golden outputs.** It proves the contracts and the
   validators, not model quality. The first real-model run is the next step.
3. **The sketch has not been flashed here** — no ESP32 toolchain in this
   environment. It passes a syntax check against stubbed Arduino headers and
   passes the project's own lint. Flashing is the immediate next task.
4. **The sonar driver is non-blocking, but the ping itself still uses two
   `delayMicroseconds` calls** of 2 µs and 10 µs. That is the datasheet
   requirement and is far below one control cycle.
